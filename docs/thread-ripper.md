- 默认：大陆节点（与上游一致；2026-10-10 至 2026-11-04 曾默认海外。上游 README「为什么用大陆 CDN」：海外边缘节点只缓存热门视频，冷门视频要绕回国内取，所以海外观看也用大陆节点、靠多线程补单连接的速度）、自动并发数（手动并发数默认 8，与上游一致）。在「设置 → 音视频设置」的 CDN 设置下方可关闭、改地区或改并发数；下次加载生效，已手动保存的设置不受影响。手动并发数只能选 4/8/16/32/64/128。
- 自动并发数默认开启（上游 userscript 的默认值；`range-core` 的 `normalizeSettings` 只在未传入时视为关闭），在 8/12/16/24/32/48/64 间调整（上游 2026.10.7.1 起上限 64，设置里标为推荐）：卡顿或低缓冲压力触发试升，10 秒无收益回退并休息 90 秒，412/429 回退并冷却 180 秒。按完整分块计有效吞吐，副本重复字节不计入；同一播放器切视频保留学习结果。拖动、打开或重载视频引起的缓冲不算卡顿，也不计入缓冲压力，对应上游忽略 `video.seeking` 期间的等待。
- 起播加速（上游 2026.9.29.1）：每次开始播放先用至少 16 线程，不越过被 412/429 拒绝的档位；前方缓冲到 15 秒后每 2.5 秒降一档，回到开播前的线程数。期间卡顿照常加档并结束起播；30 秒还没跟上就保持当时的线程数。起播中再次开始播放时，仍以第一次之前的线程数为准。
  原生适配：上游在新视频、换清晰度和拖到未缓冲位置时开始起播。这里新视频和换清晰度各建一个代理会话，代理启动即开始起播；mpv 只在缓存里没有所需数据时（拖到缓存外、重载）才对同一轨道发新的 GET，代理以此代替上游的「拖到缓冲外」判断，缓存内拖动不触发。
  上游的缓冲目标是 45 秒，15 秒约为三分之一；mpv 默认只缓冲 16 秒，并受 4 MB 前向缓存限制（码率超过约 2.2 Mbit/s 时到不了 15 秒）。所以 mpv 报告 `demuxer-cache-idle`（缓存已按设置装满、暂停读取）时也算已经跟上，否则高码率视频的起播会一直停在 16 线程。
- 剧集加速（上游 2026.10.8.1，默认开启）：番剧、电影、纪录片等剧集（PGC）走代理，可在设置里单独关闭；关闭后剧集直连，普通视频不受影响。
  与上游一致，播放地址标有 `is_drm`（数字版权保护）或 `is_preview`（只能试看）的剧集不走代理。上游剧集只用兼容模式接管，
  这是网页播放器的限制；原生播放器只有一种接入方式，剧集与普通视频使用同一个代理。
- 新增自定义节点，非空时只使用所选服务器（包括元数据探测）；清空恢复大陆/海外模式。最多 32 个，按上游媒体域名白名单校验，签名地址不会发送给任意网站。
- DASH 音视频共享连接预算。8 并发时普通请求最多占 7 个连接，保留 1 个救援连接；
  视频分块预算 6；音频至少保持 2 块在途，让一块的往返与另一块的传输重叠。队列按原版优先级排序，同优先级按进入顺序调度。
- 元数据按 0/120/300 ms 启动最多三个副本。mpv 从文件开头打开轨道时，元数据请求直接取前 64 KiB 并兼作首块，
  省去一次 1 字节探测往返；其余请求的首个 64 KiB 媒体块立即抢跑最多八个候选。
  启动后续块按已证实节点的速度分配，250 ms 后开始判断是否启动备用副本；常规块的判断时刻根据实测块耗时调整为 250–900 ms。
  到点后按上游 `hedgeDue` 去掉播放截止时间的规则判断，此后每 50 ms 再判断一次：副本节点尚未测速时到点即启动（试探更快的节点）；
  否则只在主请求已停住（一个延迟内没有新数据）、比本线路的连接通常速度慢四成以上或比副本节点的实测速度慢（副本快 1.5 倍以上）时启动。
  还没收到响应体时，要等到本线路响应头通常耗时的 1.5 倍；速度从收到首个字节起算，传满一个延迟后才评判；主请求还在排队等连接时不启动副本。
  原先到点一律启动副本，链路本身是瓶颈时几乎每块都超过 900 ms，副本占去约三成带宽，播放反而卡顿。
  成功后取消其余副本。首响应超时 5.5 秒（建连与等待响应头合计，与上游一致）、流停滞 4 秒、单次尝试 15 秒，
  最多三轮重试，轮间等待 500/1000 ms。
- 节点选择对应原版 `startupCandidates`、`rangeCandidates`、`rescueCandidates`、
  `ordered` 和 `pieceCandidates`：包含海外四轮/大陆一轮预热、分块候选交错、
  健康度排序、轮换以及下载期间重新检查封禁。预热后最多选择六个节点，保留未测速节点的探索位置。
- 按上游平滑加权轮询分配子块，快节点多领任务；慢于最快节点十二分之一的节点暂不分配主请求。测速 90 秒后过期重试，换签名保留同节点/文件的速度历史，至少 48 KiB 的传输才更新测速。备份副本优先使用最快已知节点。
- 重试和备用副本保留已校验响应中连续收到的前缀，达到 32 KiB 时只请求缺失尾部。副本取得连接后才确定续传起点；跨节点仍校验总长度，超长/错误区间响应不进入可续传前缀。
- 严格校验 HTTP 206、Content-Range、分块实际长度和跨节点资源总长度；拒绝 200、
  错区间、截断、超长响应。响应头不对的响应不会有任何字节交给播放器；分块边收边转后，
  超长响应要到收完才能发现，此前转出的只是所请求区间内的字节，多出的部分不会转出。
- 使用上游的大陆/海外节点名单、签名路径保留、Akamai-only 地址合成、失败节点退避及每视频封禁（区分节点、地址与节点/地址组合）。
  中继地址（`mcdn.` 域名、`/v1/resource/` 路径或 `os=mcdn`）带着中继自己的路径和签名，普通节点会拒绝（403），
  所以只用普通地址合成其他节点；B 站只给中继地址时，不论地区都用这些中继兜底。
  元数据候选包括原始 API 地址；媒体候选按原版地区规则过滤。
- 原生适配边界：mpv 决定读取、拖动及缓冲，不能直接复用浏览器的 SIDX/MSE
  SourceBuffer 调度。代理将开放式 Range 拆成约 2 MiB 的视频窗口，按预算分块，
  最小块按连接测速自适应为 64 KiB–1 MiB，最终分块同时考虑窗口长度和连接预算。音频块至少 256 KiB，
  连接快时按测速增大到 1 MiB；原先每个往返只取 64 KiB，高延迟线路上音频被限制在约 1 Mbit/s。
  每输出一块立即补充下一块，保留背压且不缓存整部视频。原版按 SIDX 段大小分块，
  原生代理则按字节窗口分块；两者并非逐请求相同。
  按文件顺序输出时，正在下载的队首分块收到多少就先交给 mpv 多少，取各副本中收得最多的那个，不再等整块下完。
  原先整块交付：音频开头 64 KiB 只够播约 1.6–2.6 秒，下一块 256 KiB 要和十几个视频分块分带宽，
  带宽有限时整块下完要好几秒，开播约 2 秒就因音频耗尽而音画一起停住（fork issue #5）。
- 额外的原生保护：普通连接上限在整个代理会话统一执行，避免多个开放式 Range
  同时下载时挤占救援连接。成功读完的 HTTP 请求不再调用 abort，允许连接复用。
- 代理接管每个请求的 socket 并监听读端，mpv 断开连接（拖动、解复用器重连）时立即取消该请求的全部下载。
  dart:io 的 HttpServer 在响应进行中不会报告客户端断开（写入被静默丢弃或 flush 永不返回），
  修复前被丢下的请求会一直下载到文件末尾。mpv 每条轨道只用一个连接，并且先发新请求再关旧连接，
  所以同一轨道的新 GET 请求一到就取消旧请求。更换播放源或关闭播放器会取消整个代理会话。
- 本地文件、直播、非 DASH 视频继续走原生直连。启动代理失败时使用原始播放地址；
  下载耗尽重试时返回 HTTP 错误，由播放器现有错误/重试处理接管；「视频链接打开失败，重试中」
  也匹配 `http://127.0.0.1` 代理地址。
- 适配范围不是整份 userscript：网页悬浮按钮、网页设置入口、MSE 会话/缓冲修复、网页 HLS 直播模块和网页播放清单地址刷新不接入原生播放器。原生字节请求没有 SIDX 分段的播放截止时间，不虚构时间戳套用 0.9.4.1 的网页截止时间对冲策略；备用副本采用上游 `hedgeDue` 中与截止时间无关的判断（见上），而不是上游兼容模式/桌面客户端到点即复制的固定延迟。DASH 地址生命周期仍由 PiliPlus 管理。
- 原有卡顿定时器、画面冻结检测、自动修改 CDN 设置、重载和撤销提示均已删除。
  旧置顶、排序、自定义 CDN 弹窗及其配置读取代码也已删除，手动 CDN 界面恢复上游实现。
  线程撕裂者启用时独立选择 DASH 下载节点。旧版存储的置顶键不再被读取。
- 保留独立的 URL 正确性修复及其测试：音频 CDN 绕过、P2P 地址切换时使用 HTTPS
  并清除非标准端口、缺少主机参数时的安全回退。这些代码不包含卡顿检测或自动轮换。

下载核心是独立的纯 Dart 包 `packages/thread_ripper`（只依赖 `dart:io`），不用编译 Flutter 和原生插件。
回归测试：在 `packages/thread_ripper` 下运行 `dart test`；主项目里相关的是 `flutter test test/video_utils_test.dart test/playurl_flags_test.dart`。
测试使用本地 HTTP 服务模拟正常、慢、拒绝、错误 Range、截断、资源大小变化、取消、
客户端断开和新请求取代旧请求。

## 逐行移植的下载器（`packages/thread_ripper/lib/btr/`）

`range_proxy.dart` 的下载调度是按原版思路重写的，不是逐行移植。`lib/btr/` 是原版 `idm-downloader.js`
（2026.11.3.1）的逐行移植，函数、常量、注释和顺序都跟原版一致，原版的一处 diff 可以直接对到这里：

- `downloader.dart`：`Semaphore`、`createDownloader` 的全部内容（分块、对冲副本、续传前缀、重试轮次、
  起播探测、截止时间与排队优先级、任务分配、按序交付）。时钟由外部注入，对应原版的 `performance.now()`。
- `errors.dart`：原版依赖的浏览器原语，按原版用到的语义实现：`DOMException`（按名字区分 AbortError/TimeoutError，带 HTTP 状态）、
  `AbortController`、`Promise.any`（`AggregateError` 保持尝试顺序）。
- `fetch.dart`：`fetch` 和响应体 reader 的形状与浏览器相同，`readBody` 因此可以逐行照搬。
- `range_core.dart`：`parseContentRange`、`splitRange`、`concatChunks`。
- `resolver.dart`：原版下载器对 resolver 的接口约定；`RipperCdnResolverAdapter` 把 `RipperCdnResolver`
  （连同封禁名单）接到这个约定上。

自动线程数仍用 `auto_concurrency.dart`，新增 `subscribe`，每个下载器像原版一样订阅线程数变化。
App 走 `lib/btr/range_proxy.dart`（`BtrRangeProxy`），对应原版兼容模式（`native-range-transport.js`）：
播放器自己解码、缓冲和拖动，这里只下载它的媒体请求。原版每个 DASH 分段发一个有界请求；mpv 对每条轨道用一条连接发开放式 Range（`bytes=N-`），
所以一个请求按有界窗口依次调用 `downloadRange`：视频每个请求的第一个窗口 1 MiB、之后 2 MiB，音频 128 KiB、之后 256 KiB
（原版只交付完整分块，音频窗口短，音频才不会等一个和视频分带宽的大分块，见 fork issue #5）。窗口接在上一个窗口结尾时不是起播，
否则按原版的起播处理（竞速开头再分块）；只有新的起点才调用自动线程数的 `newSession()`。第一次请求先用 `kind: "meta"` 取开头 64 KiB
（三个节点错开竞速）得到文件长度，这段数据同时作为响应开头；HEAD 只取 1 字节。响应头等第一块数据就绪才发，之前失败返回 502，之后失败直接断开。
接管 socket 察觉 mpv 断开、新请求取代同轨道旧请求、Range 解析与 416 沿用 `range_proxy.dart`。真实网络请求在 `lib/btr/http_fetch.dart`，
行为与浏览器 fetch 一致（取消时挂起的请求和读取以取消原因失败；dart:io 在响应头之后取消不会让响应体报错，由读取器自己监听取消）。

与浏览器的差异：dart:io 的 HttpClient 只有 HTTP/1.1，每个线程是一条 TCP 连接，取消一个传到一半的副本要断开连接、下一个请求重新握手；
浏览器的 HTTP/2 只关闭一条流。原版的对冲策略因此在这里更贵。原版 fetch 的 `priority` 没有对应。
旧的 `range_proxy.dart`（fork 自己写的下载调度）暂时保留作对照，App 不再使用。

### 下载器对照测试

`test/fixtures/btr_scenarios.json` 是一组模拟网络剧本：每个节点的响应头耗时、每块大小和间隔，
某个节点或某个请求返回错误状态、中途停住、提前断开、`Content-Range` 不对、网络错误，
以及什么时候调用 `downloadRange`、什么时候取消、播放器什么时候报告卡顿和缓冲。
`tool/generate_btr_traces.cjs` 把原版三个文件加载进 Node 的 `vm` 沙盒，替换掉定时器和时钟，在虚拟时间上跑完每个剧本，
记录每个请求的发出与取消（时间、节点、字节区间、原因）、交给调用方的每一块、自动线程数的变化和最终结果，
写入 `btr_traces.json`；`test/btr_downloader_trace_test.dart` 用 `fake_async` 在同样的规则下跑 Dart 移植，要求逐条相同
（同一毫秒内的事件不比较先后）。两边的模拟网络规则写在 `generate_btr_traces.cjs` 开头和 `test/btr_harness.dart`，改动时要同步。

模拟网络返回的 Promise 必须来自沙盒自己：`await` 别的环境的 Promise 会多两次微任务，改变原版自己的执行顺序
（例如起播探测的输家是否赶在任务分配之前记下测速）。浏览器里的 `fetch` 返回的都是页面自己的 Promise。

更新：`node packages/thread_ripper/tool/generate_btr_traces.cjs <上游源码目录>`。
试新剧本：把 `btr_scenarios.json` 放到别的目录，设 `BTR_FIXTURES=<目录>` 后运行生成脚本和 `dart test test/btr_downloader_trace_test.dart`。

覆盖情况：逐个改动下载器里的 20 处（常量、规则、上报），其中 17 处会让对照测试失败（含 `assignPrimaries` 的对照数据）。
未覆盖的 3 处都只在调用方给出播放截止时间时才执行：排队紧迫度的档位、「副本节点快 1.5 倍就复制」、落后判定的 250 ms 阈值。
原生播放器和原版兼容模式一样不给截止时间。搜索过程中试过的 117 个随机剧本（含过载到分块饿死的情况）在未改动时全部与原版一致。

## 与原版的对照验证
